# Следующий этап: согласованный прогноз для сервиса

Дата планирования: 08.11.2026. Ветка `Colhound`. Статус: запланировано; перечисленные ниже исправления ещё не выполнены. Работа локальная, без коммитов по указанию пользователя.

## Цель этапа

Из проверенной модели получить корректный и понятный результат, который можно одинаково показывать в пульте и использовать в агенте: восемь прогнозов часовых отгрузок, оценка неопределённости, согласованный накопленный поток и объяснимая рекомендация.

База — LightGBM с функцией потерь Huber и профилями маршрутов. Конкурсный ансамбль v2 сохраняется отдельно. Точечный прогноз модели не подменяется медианой или прогнозом накопленного груза. Цель этапа — корректность и применимость; улучшение конкурсного score не обещается.

Основания: [ML-аудит](ml_audit_results.md). В нём выявлены два уменьшения накопленного прихода, неверное название сырого прогноза `p50`, холодный цикл 30–36 секунд и ограниченность исторической проверки.

## Очередность и результат

| Шаг | Работа | Результат | Бюджет активной работы |
|---|---|---|---|
| 1 | Уточнить выходы сервиса и миграцию потребителей | Однозначные поля и тесты контракта | 1–2 ч |
| 2 | Согласовать часовые прогнозы с получасовыми потоками | Неотрицательный поток и неубывающее накопление | 2–3 ч |
| 3 | Повторно оценить интервалы и диспетчеризацию | Сравнение до/после без подбора по оценочной неделе | 1–2 ч плюс расчёт |
| 4 | Уточнить обработку плохих входных данных | Явные ограничения и предсказуемые ошибки/fallback | 1–2 ч |
| 5 | Подготовить общий снимок и убрать повторные вычисления | Данные для фронта и агента, повторное чтение без повторного dock replay | 1–2 ч |

Сроки — оценка, не обещание точного времени. Расчёты выполнять последовательно с фиксацией результатов, чтобы не искажать замеры производительности. Разработка агента другим участником может идти параллельно по согласованным полям; автоматически сообщения ему не отправляются.

## Шаг 1. Отделить прогноз от квантилей

Сейчас `Service.forecast` называет `p50` сырой выход Huber, хотя функция потерь Huber не гарантирует прогноз условной медианы.

- [ ] Ввести `point_forecast` — неизменённый выход бустинга после документированного fallback. Его использовать для конкурсной метрики и исходной реконструкции потока.
- [ ] `p10`, `p50`, `p90` получать из существующей калибровки ошибок на прошлом. Это оценки квантилей, а не гарантии по каждому маршруту.
- [ ] Раздельно описать точечное накопление и квантили накопленного потока. Не называть сырой накопленный прогноз `inflow_4h_p50`.
- [ ] Обновить `service.py`, экспорты CSV, `pipeline.py`, потребителей в шаблоне пульта и примеры контракта. Старые сохранённые модели/конкурсные файлы не перезаписывать. Ноутбуки проверить на использование изменённых полей и отметить совместимость.
- [ ] Проверить конечность, неотрицательность и порядок p10 ≤ p50 ≤ p90. Точечный прогноз может отличаться от медианы и не обязан лежать между p10/p90 во всех случаях.

Готово, когда один и тот же прогноз до/после изменения обозначений даёт идентичный официальный score, а поля квантилей соответствуют заявленному расчёту.

## Шаг 2. Получить согласованный получасовой поток

В данных часовые суммы перекрываются: `y[h] = x[h-1] + x[h]`. Текущая приближённая формула независимо оценивает накопление для разных горизонтов и допускает его уменьшение.

- [ ] Сохранить минимальный воспроизводимый пример обнаруженных нарушений и синтетический пример в тестах.
- [ ] Реализовать отдельное преобразование восьми часовых прогнозов в восемь неотрицательных получасовых объёмов.
- [ ] Основной кандидат — небольшая задача наименьших квадратов с ограничением `x[h] ≥ 0`, приближающая исходные часовые прогнозы суммами соседних получасов. Начальное `x[0]` — восстановленная по прошлому оценка, не наблюдаемый факт. На первом сравнении использовать фиксированные равные веса, без нового поиска гиперпараметров.
- [ ] Рассчитывать накопление только как сумму полученных неотрицательных получасовых объёмов.
- [ ] Сохранять величину отклонения восстановленных часовых сумм от исходного прогноза. При несовместимых прогнозах точное равенство всем восьми исходным значениям может быть невозможно; это нельзя скрывать.
- [ ] Проверить постоянный поток, нулевой поток, резкие пики, несовместимый первый горизонт и все маршруты последнего снимка. Сравнить ошибки накопления на истории с прежним методом.

Готово, когда нет отрицательных потоков/уменьшений накопления и измерено влияние преобразования на ошибку и время. Накопление максимумов поверх старого результата не принимать как исправление без проверки смысла получившегося потока. Исходный `point_forecast` для соревнования сохраняется отдельным полем.

## Шаг 3. Пересчитать интервалы и рекомендации

После смены преобразования прежняя калибровка накопленного потока уже не соответствует новому методу.

- [ ] На 18–24.10 откалибровать ошибки нового накопленного прогноза, на 25–31.10 оценить результат; использовать сохранённые rolling-прогнозы, без нового обучения модели.
- [ ] Проверить ширину и покрытие диапазонов по горизонту, размеру маршрута и времени суток. Дополнительно проверять неубывание накопленных квантилей и их порядок; любое согласование квантилей снова оценивать на следующей неделе.
- [ ] Повторить симуляцию при прежних параметрах вместимости/подачи и одинаковых исходных условиях. Сохранить простой/ожидание/недогруз отдельно, а не только их сумму.
- [ ] Сравнить со старым сервисом и простыми правилами. Если поток стал согласованным, но решения ухудшились, не заявлять улучшение эффекта: зафиксировать компромисс и пересмотреть преобразование на калибровочном периоде.
- [ ] Для сводки сети не складывать маргинальные p10/p90 маршрутов как квантили суммы; использовать отдельную оценку неопределённости суммы.

Готово, когда новая схема имеет собственный отчёт, калибровку и документированные ограничения. Это повторная историческая проверка, не новый holdout. Старые заявления «60 → 20 минут» автоматически на неё не переносятся.

## Шаг 4. Определить поведение при неполных данных

- [ ] Проверять свежесть всей выгрузки, пропуски target и статусов, регулярность времени и достаточность истории признаков. Нулевые значения не считать автоматически пропусками.
- [ ] Для каждого случая определить действие: обычный прогноз, проверенный fallback или явная ошибка/недоступность. Не заменять отсутствие данных нулём без обозначения.
- [ ] Неизвестные маршруты и слишком короткую историю обрабатывать явным сообщением, если для них не реализован проверенный метод прогноза.
- [ ] Описать качество диапазонов при fallback: калибровка основной модели не становится автоматически корректной для запасного метода.

Готово, когда пропуски/задержки воспроизводятся в тестах и видны в статусе снимка для фронта/агента. Исправленная ранее актуальность кэша — только часть этой задачи.

## Шаг 5. Подготовить снимок для интерфейсов

- [ ] Собрать версионированный снимок: дата данных, модель, калибровка, прогнозы, диапазоны, качество данных, сценарий и основания рекомендаций.
- [ ] В идентификатор включить версии/хеши исходных данных, модели, калибровки и параметры сценария. Кэш сценариев инвалидировать при изменении любого из этих входов.
- [ ] Снимок рассчитывать один раз; чтение карточки маршрута и вопрос агента не должны запускать 21–26 секунд dock replay заново.
- [ ] Замерить отдельно создание снимка и повторное чтение. Не обещать конкретное ускорение до измерения.
- [ ] Согласовать с `agent_contract.md`; подготовить реальные примеры ответов функций по снимку. Создание HTTP API и визуальная доработка следуют после стабилизации этих данных.

Готово, когда фронт и функции агента могут получить одинаковые значения с одинаковым snapshot/scenario ID, а исходные и симулированные величины различимы.

## Проверки и документация

Регрессионные тесты затрагивают реальные ошибки: семантику полей, согласованность потока, отсутствие будущего, плохие входы и совпадение потребителей. Не создавать тесты только ради покрытия строк.

Новые результаты сохранять в отдельном `reports/colhound/service_v2/`, большие массивы — в `.local/colhound/`. До сравнения записать manifest с датами, методами и хешами; после — таблицы качества, интервалы, показатели симуляции, время и `decision.md`. Предыдущий аудит `reports/colhound/ml/` оставить неизменным. Каждый завершённый шаг отмечать в `work_log.md` и основном плане.

## Отдельное улучшение конкурсного score

После этих обязательных исправлений допускается один ограниченный цикл ML, если остаётся время. Сначала разложить ошибки по горизонту, дню и размеру маршрута; выбрать одну гипотезу до запуска. Первый кандидат — осторожная калибровка уровня по прошлому, поскольку она уже показала неодинаковый эффект у разных моделей. Новые архитектуры и широкий подбор признаков в этот этап не включать.

Оценивать гипотезу на нескольких последовательных блоках при одинаковой доступности истории. Использованные даты не называть независимым holdout. При отсутствии устойчивого выигрыша сохранить базовый Huber для сервиса и v2 для соревнования. Хорошая интеграция агента не требует изменения конкурсной модели.
