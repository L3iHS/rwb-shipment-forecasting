# Сервис v2: согласованные прогнозы и общий снимок

Дата: 08.11.2026. Ветка `Colhound`, изменения локальные, без новых коммитов. Выполнены пять шагов из [плана следующего этапа](next_stage_plan.md): семантика выходов, поток, проверка, плохие входы и общий снимок. Новая ML-модель не обучалась; веса LightGBM и конкурсный ансамбль не изменялись.

## Что изменилось

**Точечный прогноз и медиана теперь разные поля.** `point_forecast` содержит исходный результат LightGBM Huber и используется в конкурсном CSV. `p10`, `p50`, `p90` получаются из калибровки прошлых ошибок. `p50` больше не маскирует сырой прогноз под медиану.

**Получасовой поток согласован.** Модуль `src/rwb/flows.py` решает малую задачу неотрицательных наименьших квадратов: соседние получасовые потоки должны приблизить восемь исходных часовых прогнозов. Предшествующий получас — восстановленная по истории оценка. Накопление — сумма неотрицательных потоков, поэтому не уменьшается. Отклонение восстановленных часовых сумм от исходного прогноза доступно как `hourly_adjustment`; исходный `point_forecast` не заменяется этим преобразованием.

**Диапазоны потока пересчитаны.** Создан отдельный пакет `models/prod/service_v2/`, прежний `models/prod/service/` сохранён. Старую калибровку накопления нельзя незаметно загрузить новым сервисом: загрузчик требует новую версию схемы и метода. Квантили накопления согласуются перестановкой по горизонтам; их покрытие проверено после преобразования. Это маргинальные диапазоны по горизонтам, не гарантии одновременного попадания всей траектории.

**Сеть имеет свою калибровку.** Квантили суммы сети рассчитываются по ошибкам суммы, а не суммированием квантилей отдельных маршрутов. Пульт больше не складывает восемь перекрывающихся часовых значений и не называет сумму p90 маршрутов вероятностной границей всей сети.

**Входы проверяются явно.** Контролируются маршруты/порядок, регулярность времён, минимальная история и конечность значений таргета/статусов. При пропусках доступен сезонный fallback только при достаточной истории; его диапазоны основной модели объявляются недоступными, в JSON это `null`. Недостоверный запасной прогноз не создаётся из нулей. Для неполной истории симуляция остатка требует отдельно предоставленного состояния склада. Запрос на более новое время проверяется через `requested_at`; постоянного live-мониторинга загрузок пока нет.

**Снимок общий для потребителей.** `src/rwb/snapshot.py` связывает исходные данные, производные массивы, код, модели, калибровку, параметры и отчёт с `snapshot_id`. Изменение любого из этих входов инвалидирует кэш. JSON записывается атомарно, проверяется контрольной суммой. Повторное чтение не запускает ML и dock replay.

Доступны Python-функции `route_status`, `find_routes`, `network_summary`, `evidence`, `what_if`. Сценарий использует тот же сервис и получает собственный ID; реальные машины не вызываются. HTTP API и LLM подключает следующий интеграционный этап/участник агента. [Текущий контракт](agent_contract.md).

## Исправление временной проверки

В прежнем rolling-протоколе последние семь начал калибровочной недели имели цели уже после начала оценочной недели. Новый прогон оставляет только окна, у которых **последняя целевая точка уже известна при первом оценочном прогнозе**. Удалены семь пограничных начал; осталось 329 калибровочных и 329 оценочных начал, по 1000 маршрутов и 8 горизонтов.

И старый, и новый методы в сравнении ниже заново откалиброваны с этим ограничением и одинаковыми группами маршрутов. Это отделяет эффект преобразования потока от изменений протокола. Калибровочные метки заканчиваются 25.10.2025 10:30, в момент первого оценочного прогноза. Эти периоды уже использовались в разработке: независимого holdout здесь нет.

## Результаты на истории

| Показатель | Старый метод с исправленной калибровкой | Новый метод |
|---|---:|---:|
| WAPE накопленного потока, все горизонты | 0.182371 | **0.181725** |
| Уменьшения накопленного потока | 1854 | **0** |
| Уменьшения медианы накопления | 847 | **0** |
| Покрытие 80%-диапазона накопления | 80.333% | 80.340% |
| Покрытие 80%-диапазона суммы накопления сети | 86.702% | 87.348% |
| Потери на машину в базовой симуляции, мин | 20.252 | 20.226 |

Покрытие сети выше номинальных 80%: это наблюдаемая консервативность на данном периоде, а не идеально откалиброванный диапазон. Часовой прогноз модели не менялся: средний официальный score в 10:30 — 0.327883, по всем началам — 0.333677. Покрытие его 80%-диапазона по маршрутам — 79.887%.

Изменение восстановленных часовых сумм составляет около 0.0064% от суммы исходных прогнозов по абсолютной величине. Эффект на симуляцию небольшой. Основное улучшение — устранение противоречивого накопления и корректный контракт, а не новый рекорд Public.

Проверены девять сочетаний вместимости и времени подачи, подробности по горизонту/размеру маршрута/часу сохранены в [каталоге отчёта](../reports/colhound/service_v2/summary.csv). Вместимость в единицах счётчиков, время подачи, начальный остаток и использование отгрузок как доступного потока — допущения симуляции. Реальная экономия не доказана.

## Сквозная проверка и скорость

В [verification.json](../reports/colhound/service_v2/verification.json) зафиксированы:

- первый CLI-запуск прогноза — 13.29 секунды, создание снимка внутри него — 8.78 секунды;
- повторный CLI-запуск — 4.65 секунды с `cache_hit=True`, включая запуск Python, загрузку данных и проверку идентификатора;
- генерация пульта с тем же снимком — 4.82 секунды;
- 8000 ID в экспорте, прогноз совпадает с архивным `lean_test.npy` с допуском на чтение CSV;
- функции для агента и CSV возвращают одинаковые значения и snapshot ID;
- JavaScript пульта выполнен в минимальном DOM Node.js, проверены первая/последняя карточки и недоступные диапазоны; NaN/undefined в рендере нет.

Это один локальный сквозной замер; его нельзя напрямую трактовать как гарантированную производительность или строго контролируемое ускорение относительно первого аудита. Визуальная проверка в браузере пока не выполнена. HTTP/LLM в этих временах отсутствуют.

63 теста проекта прошли, включая оптимальность согласования потока, калибровочную границу, сохранение/загрузку сервиса, fallback, свежесть запроса, инвалидацию/повреждение кэша снимков и пересчёт сценария.

## Воспроизведение

Из корня репозитория, в установленном окружении проекта:

Для CPU-сервиса добавлен отдельный `requirements-service.txt` с фактически проверенными версиями NumPy, pandas, PyArrow, SciPy и LightGBM. PyTorch и XGBoost для этого пути не требуются; полный конкурсный ансамбль использует исходный `requirements.txt`. Чистая установка минимального окружения здесь отдельно не выполнялась.

```powershell
$env:OMP_NUM_THREADS = '4'
$env:OPENBLAS_NUM_THREADS = '4'
$env:MKL_NUM_THREADS = '4'
python scripts/validate_service_v2.py --output .local/colhound/reproduce_service_v2
python scripts/prepare_service_v2.py
python scripts/verify_service_v2.py
```

Проверенный отчёт `reports/colhound/service_v2/` включён в Git: после клонирования можно пропустить первую команду и сразу подготовить пакет. Повторная оценка в примере пишет отдельную копию в `.local/`. Оценка и подготовка пакета требуют новых пустых выходных каталогов и не перезаписывают прошлые результаты. Основной pipeline использует `models/prod/service_v2/` и включённый отчёт `reports/colhound/service_v2/report.json`. Полный пересчёт сохранённых бустингов не требуется. Проверенный интерпретатор — Python 3.12.4 из соседнего проекта, фактические зависимости прежнего аудита — `reports/colhound/ml/manifest.json`.

Для обычного использования готового пакета:

```powershell
python scripts/pipeline.py forecast --at "2025-11-01 10:30"
python scripts/pipeline.py report --at "2025-11-01 10:30"
```

Пульт: [outputs/dispatch_board.html](../outputs/dispatch_board.html). Текущий ноутбук: [service_v2.ipynb](../notebooks/service_v2.ipynb); его ячейки проверены на компиляцию, отдельный Run All не выполнялся. `solution_service.ipynb` сохранён как явно помеченный исторический разбор v1 на commit f2dd580.

Новый модельный пакет и большие снимки находятся локально в исключённых из Git каталогах. Для передачи команде нужны новый пакет либо команда его воспроизведения, а не только изменения исходников. В `provenance.json` пакета сохранены хеши и источник калибровки. Ранее измеренные отчёты `reports/colhound/ml/` оставлены как история исходного состояния; их хеши кода относятся к тому состоянию.
