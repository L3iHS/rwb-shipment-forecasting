# Контракт сервиса, фронта и агента

Статус: v0.2 от 08.11.2026. Python-функции и общий снимок реализованы в `src/rwb/snapshot.py`; HTTP API пока нет. Разработчик агента — другой участник; провайдер LLM этим документом не выбирается. [Результаты и запуск](service_v2_results.md).

Текущие функции принимают готовый snapshot как первый аргумент; аргумент `snapshot_id` будущего HTTP API должен разрешаться в этот объект сервером. `what_if` дополнительно получает store/service/panel/cums/origin, то есть зависимости сервиса, которые нельзя принимать как произвольный код из запроса LLM. Его параметры — `lead_minutes`, опциональные `fill_hours` и `route_id`. Вместимость пока выражена часами среднего потока, не реальными кубометрами.

Поле сырого прогноза — `point_forecast`, `p50` — оценённая медиана. Накопление — `inflow_point`, отдельно `inflow_p10/p50/p90`. При fallback квантили имеют JSON null и `intervals_valid=false`. `network_summary` возвращает отдельно откалиброванные квантили суммы сети. `evidence` поддерживает темы model, validation, dispatch, assumptions при подключённом отчёте. Подробные примеры находятся в `notebooks/service_v2.ipynb`.

## Общий источник цифр

ML формирует снимок данных и прогноза, который используют пульт и функции агента. Снимок содержит `snapshot_id`, `as_of`, `model_id`, `data_version`, `calibration_version`, единицы счётчиков и параметры сценария. Изменение параметров создаёт `scenario_id` и не переписывает базовый снимок.

Времена данных timezone-naive: часовой пояс не объявлять московским без подтверждения. Рабочий объём счётчиков не выдавать за массу, кубометры или реальные типоразмеры кузовов. Остаток и вместимость из симуляции помечать соответствующим происхождением.

## Функции для LLM

| Функция | Аргументы | Результат |
|---|---|---|
| `route_status` | `snapshot_id`, `route_id` | История, 8 прогнозных точек, диапазоны, план вызова, причины по правилу и допущения |
| `find_routes` | `snapshot_id`, фильтр `call_now / within_hour / stale`, `limit` | Отсортированные маршруты с причиной попадания в список |
| `network_summary` | `snapshot_id` | Сводка сети по каждому горизонту, маршруты внимания, состояние данных |
| `what_if` | `snapshot_id`, `route_id`, `lead_minutes`, опциональный сценарий вместимости | Новый план с `scenario_id`, исходными параметрами и числовой разницей |
| `evidence` | `snapshot_id`, тема `model / validation / dispatch / assumptions` | Метрики, период, метод расчёта, ссылка на артефакт и ограничения |

В первой интеграции обязательны `route_status`, `find_routes`, `network_summary`, `evidence`. `what_if` подключить до сдачи, если корректный пересчёт сценария прошёл проверку; иначе явно сообщать о недоступности и оставить в roadmap.

Каждый ответ инструмента возвращает `snapshot_id` и ссылки `evidence_ids`. Для списков действуют пагинация/лимиты; агент не получает всю матрицу истории по 1000 маршрутам в каждом запросе. Нельзя суммировать восемь перекрывающихся `target_1h` как уникальные отгрузки за четыре часа; для накопленного потока используется отдельный согласованный показатель.

## Предлагаемый интерфейс фронта

Сервисные чтения: `GET /api/v1/snapshot`, `GET /api/v1/routes`, `GET /api/v1/routes/{route_id}`, `GET /api/v1/evidence`; пересчёт — `POST /api/v1/scenarios`. Пути согласовать с участником до реализации.

Чат: `POST /api/v1/chat`. Минимальное тело:

```json
{
  "message": "Почему по маршруту предлагается вызвать машину сейчас?",
  "snapshot_id": "<идентификатор реального снимка>",
  "route_id": 123,
  "conversation_id": null
}
```

`route_id` — пример, не утверждение о существовании маршрута. Сервер проверяет его по выбранному снимку. Запрос не принимает готовые доверенные метрики или системные инструкции от клиента.

Ответ чата: `answer` (текст), `snapshot_id`, `conversation_id`, `evidence_ids`, `tool_results` (только необходимые проверяемые поля), `suggested_actions` (переход к маршруту или сценарию). Числа имеют значения, единицы и provenance; пользовательские строки не вставлять в HTML без безопасного вывода.

Ошибки: машинный `code`, понятный `message`, `retryable`, `request_id`. Минимум: неизвестный маршрут, устаревший/отсутствующий снимок, некорректный сценарий, timeout LLM, недоступный инструмент. При ошибке LLM прогноз и пульт продолжают работать.

## Граница ответственности агента

LLM выбирает функции и объясняет возвращённые цифры. Прогноз и план рассчитывает сервис. Для «почему вызвать сейчас» возвращать backlog, ожидаемый приход за lead time, вместимость, уже вызванные машины и условие срабатывания правила. Это объяснение решения диспетчеризации; причинное объяснение ML-прогноза без отдельного анализа не обещается.

Агент не совершает реальный вызов транспорта. API-ключ находится в серверном окружении; клиент обращается к серверу. Нужны ограничение времени/числа вызовов инструментов и размера ответа. Offline-режим пульта не выдаётся за работающий онлайн-чат.

## Приёмка интеграции

- По одному маршруту значения фронта, инструментов и ответа совпадают с учётом только форматирования.
- Контекст выбранного маршрута передаётся в чат; смена снимка не смешивает старые и новые ответы.
- Проверены 10 вопросов: 3 о маршруте/рекомендации, 2 о списках, 2 о сети, 1 о качестве, 1 о недоступных данных, 1 о сценарии.
- Каждый числовой ответ имеет источник в результате функции; недоступный сценарий явно обозначается.
- Проверены неверный ID, timeout, недоступный сервер, повтор запроса и устаревший снимок.

Изменения контракта отмечать новой версией здесь и в `work_log.md`; до реализации синхронизировать обе стороны.
