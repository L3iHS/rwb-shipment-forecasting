# План реализации Colhound: ближайшие 48 часов

Создан 08.11.2026. Рабочая ветка: `Colhound`, база: `feat/forecast-models`, commit `f2dd580`.
Горизонт — два дня по запросу команды. Точное время сдачи отдельно не подтверждено; интервалы ниже отсчитываются от начала реализации.

## Результат к сдаче

Рабочий прототип: прогноз на 4 часа по 1000 маршрутам, пульт диспетчера, подключённый агент другого участника и паспорт проекта с проверяемыми результатами. Конкурсный ансамбль v2 сохраняется как ориентир с сообщённым Public 0.323. Сервисную модель выбираем по качеству и стоимости запуска. Её результат не подменяем оценкой ансамбля.

Агент входит в обязательный командный объём по указанию пользователя. Презентацию откладываем до следующего этапа. Реальную интеграцию со складскими системами, полную диспетчеризацию автопарка и широкий поиск новых архитектур переносим в roadmap.

## Распределение работ

| Направление | Ответственный | Зона изменений |
|---|---|---|
| ML-аудит, выбор модели, сервисные вычисления, документация | Colhound / Codex с пользователем | `src/rwb/`, `scripts/`, `tests/`, `docs/` |
| Пульт и подключение чата | Colhound / пользователь | Шаблон пульта и адаптер обращения к агенту |
| LLM API, вызовы функций, формирование ответа | Другой участник команды | Собственный модуль агента, согласованный API |
| Проверка паспорта и итоговой комплектации | Команда | Фактические авторы, требования формы сдачи, комплект файлов |

Это распределение задач, а не запуск дополнительных агентов Codex. До совместного редактирования закрепить границы файлов; чужой модуль агента не переписывать. Для интеграции согласовать коммит участника и переносить его явно, с проверкой контракта.

## Последовательность и зависимости

### Этап 0 — зафиксировать исходное состояние, часы 0–2

- [x] Создать ветку `Colhound` от готового прототипа.

Выход: общая исходная точка и согласованный интерфейс. Последние два пункта выполняет команда; отправка сообщений участникам автоматически не производится.

### Этап 1 — качество и корректность ML, часы 2–10

- [ ] Сравнить v2, обычный Huber и Huber с профилями по [протоколу](ml_validation_protocol.md).
- [ ] Проверить хронологическую калибровку; широкий подбор параметров не запускать.
- [ ] Проверить `p50`: сырой точечный прогноз отделить от оценённой медианы. Сохранить точечный прогноз для метрики и отдельно определить поля квантилей; обновить всех потребителей.
- [ ] Проверить накопленный приход: неотрицательность, монотонность, соответствие получасовым потокам. Метод согласования выбрать по тестам и повторной оценке; простое накопление максимумов не считать автоматически корректным решением.
- [ ] Обеспечить актуальность кэша по входным данным; проверить пропуски target и статусов, задержку выгрузки, короткую историю и неизвестные маршруты.
- [ ] После изменений пересчитать затронутые интервалы и симуляцию. Старые цифры эффекта не переносить на изменённый сервис без проверки.

Выход: выбранная версия сервисной модели, зафиксированные ограничения и регрессионные тесты значимых случаев.

### Этап 2 — единый слой данных, часы 6–14

После фиксации семантики полей; разработка адаптеров может начинаться по контракту раньше.

- [ ] Ввести идентификатор снимка: данные + модель + калибровка + параметры сценария.
- [ ] Реализовать `route_status`, `find_routes`, `network_summary`, `what_if`, `evidence` поверх общего сервисного слоя. Намеченные файлы: `src/rwb/api.py`, `src/rwb/tools.py`; окончательные имена зафиксировать перед реализацией.
- [ ] Добавить запуск локального HTTP-сервиса без обучения при каждом запросе; модель загружается один раз, снимок переиспользуется.
- [ ] Версионировать контракт, примеры ответов и ошибки; реализовать тесты схем и совпадения цифр с сервисом.

Выход: фронт и агент читают один снимок и получают одинаковые цифры. Библиотеку HTTP-сервера выбрать при реализации с учётом окружения, добавить зависимость явно.

Агент — задача другого участника:

## Критерии готовности

| Область | Проверяемое условие |
|---|---|
| ML | Одинаковые временные окна, сохранённые прогнозы/метрики и границы обучения; решение о выборе модели записано |
| Модель | Сохранение/загрузка даёт тот же прогноз; CPU-запуск измерен; комплект не требует обучения ансамбля для демонстрации |
| Корректность | Обозначения точечного прогноза/квантилей верны; приход согласован; пропуски и устаревшие данные не маскируются |
| API | Фронт и инструменты агента ссылаются на один снимок; сценарии отделены от исходного прогноза |
| Агент | Реальные вызовы LLM и функций; числовые ответы проверены; секретов в клиенте нет |
| Пульт | Рабочий основной сценарий и состояния ожидания/ошибки; цифры соответствуют API |
| Паспорт | Каждое утверждение о качестве/скорости/эффекте имеет источник; планы отделены от реализованных функций |

## Если времени не хватает

Сохраняем: проверенный прогноз, корректный основной пульт, подключённый агент с минимальным набором функций, паспорт и воспроизводимый запуск. Сокращаем визуальные украшения, дополнительные графики, сложные сценарии агента, дистилляцию и новые модели. Непроверенные функции остаются в roadmap и не отмечаются выполненными.
