# Протокол выбора ML-модели для сервиса

Статус: план, 08.11.2026. Ветка `Colhound`. Цель — обосновать сервисную модель к ближайшей сдаче, сохранив конкурсный результат v2.

## Исходная проверка

Ранее в этом чате независимо пересчитаны сохранённые OOF-прогнозы ветки `feat/forecast-models`. Среднее официальной метрики по дням:

| Модель | 18–24.10.2025 | 25–31.10.2025 | Все 14 дней |
|---|---:|---:|---:|
| v2 с финальными весами | 0.324528 | 0.329007 | 0.326768 |
| Huber | 0.327625 | 0.329124 | 0.328374 |
| Tweedie | 0.325394 | 0.330211 | 0.327802 |
| Huber с профилями | 0.326413 | 0.327883 | 0.327148 |

Источник: `models/oof/*.npz`, веса `submissions/ensemble_v2.json`; имя сервисного кандидата `lgbm_huber_blr`. Его конфигурацию нужно сверить с пакетом `models/prod/service/model/forecaster.json`, а не предполагать идентичность по имени.

Веса v2 выбраны на этих датах. Среднее 0.326768 — оценка с финальными весами на данных разработки. Записанная cross-fitted оценка v2 — 0.328830. Public 0.323 сообщён командой и относится к ансамблю, не к Huber. Разрыв 0.00038 не является доказательством эквивалентности моделей на новых данных.

## Кандидаты и бюджет

Обязательные: v2, Huber с профилями и обычный Huber как контроль. Tweedie — дополнительный кандидат при наличии воспроизводимых результатов. До завершения этого сравнения новые семейства не добавлять.

На новые обучения и калибровочные проверки выделить до четырёх часов вычислений в первом дне; при превышении ограничить число запусков и записать покрытие. Дистилляцию рассматривать только после основных критериев готовности, без обязательства уложить её в эту сдачу.

## Временная проверка

1. Составить журнал ранее просмотренных окон по трём веткам. Уже известные октябрьские окна использовать как development, не называть новым holdout.
2. До просмотра новых результатов записать manifest запуска: даты, кандидаты, параметры, калибровочные периоды, train cutoff, seed и критерии выбора. Проверить достаточность истории для каждого окна.
3. Сначала воспроизвести сравнение на октябре. Затем проверить несколько хронологических блоков, в том числе за пределами октября. Даты выбрать по журналу использования до расчёта; уже исследованные периоды отметить как повторную историческую проверку. При отсутствии нетронутого периода явно записать это ограничение.
4. На каждом блоке модель обучается по уже известным меткам; признаки доступны только на момент прогноза. Проверять совпадение режима переобучения с предполагаемым сервисом.
5. Для калибровки использовать только предыдущий блок. Веса v2 тоже должны быть получены до оценочного блока. Если невозможно пересчитать ансамбль, отдельно показать сравнение с замороженными весами и обозначить его ограничение; оно не заменяет строгую проверку.
6. Начала в 10:30 считать основным конкурсным срезом. Для сервиса дополнительно оценить разные часы; не смешивать их в одну неразмеченную оценку.

## Метрики и измерения

- Основная метрика: среднее дневных WAPE + |Relative Bias| по одинаковым 8000 точкам.
- Отдельно: WAPE, signed bias, абсолютный bias, худшие дни, парные разницы между моделями; pooled score — дополнительный показатель.
- Диагностика по горизонту и размеру маршрута. Пересекающиеся окна не считать независимыми наблюдениями для статистических выводов.
- Диапазоны: покрытие и ширина по горизонту/группам/периоду. Калибровочные данные предшествуют оценке.
- Время: чтение входов, признаки, модель, восстановление состояния, план; холодный и тёплый запуск отдельно. CPU, RAM, размер пакета и версии окружения записать.
- Сохранение/загрузка: совпадение прогнозов с заданным численным допуском.

## Правило решения

Рабочий инженерный допуск к среднему score ансамбля: +0.002 абсолютных единицы. Это предлагаемый порог выбора для данной сдачи, не статистическая граница и не установленное правило соревнования. Зафиксировать его в manifest до новых результатов.

Если сервисный кандидат укладывается в допуск на согласованной оценке, не имеет необъяснённых провалов и даёт измеренное преимущество по запуску/зависимостям, выбрать его для прототипа. Конкурсный v2 сохранить отдельно. Если кандидат хуже допуска, проверить калибровку только на прошлом; при отсутствии улучшения записать компромисс и не заявлять близкое качество без оснований. Сложность ансамбля сама по себе не доказывает непригодность для эксплуатации.

Финальное решение должно включать число проверенных дней, режим обучения и ограничения. Изменения после проверки требуют повторной оценки затронутой части.
