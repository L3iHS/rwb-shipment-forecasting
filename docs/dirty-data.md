# Грязные данные на вкладке «Свой файл»

Перед моделью файл проходит проверку (`src/rwb/checks.py`): она читает файл в любом из привычных видов, сверяет его с историей и чинит то, что решают сам файл и история, без догадок. Что решить нельзя, остаётся как есть и помечается. Каждая правка выводится на экран под прогнозом («Проверка файла») и доступна ассистенту.

## Как проверяли

Взяли демо-файл затора (`frontend/public/demo/zator_0900-1030.csv`: 1000 маршрутов, 09:00–10:30, на 200 маршрутах сортировка падает до 5 %) и испортили его так, как портят настоящие выгрузки. Хороший ответ на испорченный файл — прогноз чистого файла. Сравнение по объёму сети за 4 часа и по объёмам маршрутов (сумма |испорченный − чистый| / сумма чистого). Всё считает тот же движок, что отвечает на `/api/forecast`:

```bash
backend/.venv/bin/python scripts/dirty_upload.py
backend/.venv/bin/python scripts/dirty_upload.py --write
```

Второй вызов ещё и сохраняет все случаи в `data/processed/dirty/` (чтобы загрузить руками на вкладке) и демо «Грязная выгрузка» в `frontend/public/demo/gryaznyi_0900-1030.csv`.

## Что проверка не правит

- Файл, который нельзя прочитать: Excel (`.xlsx`, просит сохранить как CSV), файл без статусов и отгрузок (как `test`), колонка, где больше половины значений не числа, время, которое не читается в большинстве строк, шаг не 30 минут.
- Спорное: две строки с одним маршрутом и временем, но разными числами. Берётся нижняя строка, на экране предупреждение.
- Сценарии. Затор, всплеск, рост отгрузок вдвое меняют данные намеренно: проверка их не трогает. Выбросом считается только значение выше максимума маршрута за 4 недели больше чем в 10 раз; единицы правятся, только если весь столбец отличается от истории в 1000 раз.
- Сдвиг времени и получасовой `target_1h` находятся по совпадению с историей. Если файл целиком после конца истории, сверять не с чем, и такой файл читается как есть.
