# Пульт диспетчера: устройство

Здесь — как приложение устроено и что умеет бэкенд ассистента.

## Состав

```
scripts/pipeline.py export  ->  frontend/public/board.json  ->  frontend/ (React)  ->  frontend/dist/
                                         \-> backend/ (FastAPI: /api/agent + раздача frontend/dist)
```

- `pipeline.py export` строит данные экрана и пишет их в JSON.
- `frontend/` — React 18 + TypeScript + Vite, Tailwind, Motion для переходов; графики нарисованы в SVG вручную (`frontend/src/components/charts.tsx`), шрифты Sofia Sans (три ширины) и Martian Mono лежат в сборке. Читает `board.json` при загрузке. Цвета, типографика и правила движения — дизайн-система «Ночная смена», токены в `frontend/src/index.css`.
- `backend/` — FastAPI: `app.py` (маршруты `POST /api/agent` и `POST /api/forecast`, лимиты запросов, раздача собранного фронта), `tools.py` (функции ассистента поверх `board.json`) и `forecast.py` (сервисная модель для вкладки «Свой файл»).
- `Dockerfile` в корне собирает фронт и запускает бэкенд в одном контейнере на порту 8000.

Запуск:

```bash
cd frontend && npm install && npm run build
cd ../backend && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app:app --port 8000
```

Пульт открывается на `http://localhost:8000`. Ключ Claude — в `backend/.env` (образец `backend/.env.example`); без него ассистент отвечает на типовые вопросы сам. Данные пульта обновляет `python scripts/pipeline.py export`. Для разработки фронта — `npm run dev` в `frontend/` (порт 5173, `/api` проксируется на 8000).

Контейнер:

```bash
docker build -t rwb-dispatcher . && docker run -p 8000:8000 --env-file backend/.env rwb-dispatcher
```

## Данные `board.json`

Единица объёма — товары. Шаг — 30 минут, `now` — момент прогноза (последняя точка истории).

| Поле | Что это |
|---|---|
| `now`, `step_min`, `hist_n` | момент прогноза, шаг, сколько точек истории у каждого ряда |
| `model` | `trained_until`, `lib`, `objective`, `lead_h` (подача машины), `fill_hours` (кузов в часах среднего потока), `max_wait_h`, `risk` |
| `network` | `hist` — сумма `target_1h` по сети за 16 шагов; `p50`, `lo`, `hi` — прогноз сети на 8 шагов и диапазон 10–90 % |
| `routes[]` | по маршруту: `id`, `cap` (вместимость кузова), `bl` (груз у ворот в кузовах), `way` / `dock` (машин в пути / у ворот), `call` (шагов до вызова, 0 — сейчас, −1 — не нужен в горизонте), `h` (история `target_1h`), `p10` / `p50` / `p90` (прогноз `target_1h`), `c50` / `c90` (накопленный приток к воротам за 1..8 шагов, медиана и осторожный сценарий), `cr` (приток, по которому правило решает о вызове: откалиброванная медиана), `wape` / `bias` (ошибка маршрута и сдвиг его суммы на проверочной неделе) |
| `monitor[]` | журнал качества проверочной недели: `day`, `wape`, `bias`, `cov` (попадание в 80 % диапазон) |
| `alerts[]` | тревоги монитора |
| `backtest` | `sensitivity` — потери на машину (мин) для правил при разных `lead_h` и `fill_hours`; `per_day` — машины, простой, ожидание, недогруз по правилам; `intervals` — заявленное и фактическое попадание; `point` — метрика по всем моментам прогноза, `point_1030` — только из 10:30, как в тесте; `week` — даты недели |

Поля машин и вызова (`cap`, `bl`, `way`, `dock`, `call`, `c90`, `cr`) экран и ассистент больше не используют; их считает `rwb.dispatch.call_plan`: следующая машина нужна, когда груз у ворот плюс приток покрывают на кузов больше, чем уже вызвано; вызывать её нужно за время подачи до этого момента. По `cr` при исходной подаче результат совпадает с полем `call` у всех 1000 маршрутов.

## Экран «Прогноз»

Главный экран показывает прогноз и то, насколько ему можно верить; вызова машин на экране нет. Так решено 10.11: организаторы оценивают метрику, а время подачи и вместимость машин в данных не заданы, это условные параметры (см. `docs/defense.md`, вопрос «Откуда вместимость машин и время подачи?»).

Сверху слева сколько товаров отгрузят до конца горизонта (сумма `c50` за 8 шагов по всем маршрутам), пик в час и число маршрутов; справа проверка на неделе, которую модель не видела: метрика кейса из 10:30 (`point_1030`) и доля факта внутри коридора 80 %. Ниже общий график отгрузок: факт за 4 часа, прогноз на 4 часа с коридором, пик. Дальше список маршрутов (сортировка по объёму на 4 часа, ошибке на проверке или номеру, поиск по номеру) и карточка выбранного маршрута: объём на 4 часа, пик, ширина коридора, ошибка и сдвиг на проверке, график факт и прогноз. Таблица «По дням проверки» — ошибка, сдвиг суммы и попадание в коридор по дням (`monitor`). Сравнение правил вызова машин (`backtest.sensitivity`) осталось в данных и в `docs/defense.md`, на экране его нет.

Раскладка зависит от ширины самого экрана, а не окна: на `<main>` стоят контейнерные запросы, размеры главной цифры, заголовка и колонок заданы через `clamp()` в долях ширины (`cqw`). Ассистент на экране от 1280 px занимает 420 px справа, а экран плавно сжимается; на экране уже 1280 px ассистент открывается поверх.

## Вкладка «Свой файл»

Та же сервисная модель (`models/prod/service`, LightGBM Huber), что построила `board.json`, но на данных, которые загружает пользователь. Переключатель «Смена / Свой файл» в шапке, адрес вкладки `#file`.

Результат показывается тем же экраном «Прогноз», только по данным файла. Что изменил файл: в заголовке объём на 4 часа и его изменение против исходного прогноза (того, что на главной вкладке, от того же момента без данных файла); на графике пунктир «исходный» — этот прогноз, подсвеченный участок с подписью — где данные файла начинают отличаться («затор с 09:30: 200 маршрутов, обработка 5%»); в списке вместо ошибки столбец «Изменение» — изменение объёма маршрута на 4 часа, по нему список и отсортирован; в карточке маршрута тоже пунктир «исходный». Таблицы проверки здесь нет: это свойство модели, она на главном экране. «Другой файл» в шапке возвращает к выбору файла. Цвет главной цифры у файла жёлтый, чтобы вкладки не путались. Ассистент на вкладке файла отвечает без модели, из данных на экране: серверные функции модели видят только прогноз пульта, и под ответом это написано.

Файл: CSV (запятая, точка с запятой или табуляция) или Parquet с колонками train: `route_id, timestamp, status_1..6, target_1h`, шаг 30 минут, до 16 МБ и 200 000 строк. Время в ISO (`2025-11-01 10:30`) или с точками, день первым (`01.11.2025 10:30`); время с часовым поясом переводится в московское. Строки внутри истории заменяют её, строки сразу после истории продолжают её (до двух суток, все маршруты на каждый шаг). Прогноз строится от последнего времени в файле и сравнивается с прогнозом от того же момента без файла. Если после конца файла в истории уже есть данные, на графике видно и то, что было на деле.

Груз у ворот и машины в пути берутся как на пульте, пока файл не меняет `target_1h`: это факт склада, а не прогноз. Если отгрузки в файле другие, состояние ворот пересчитывается по ним (+3 с).

`POST /api/forecast`: тело запроса и есть файл. Ответ — `src/rwb/upload.py` `compare()`: все маршруты в формате `board.json` (`routes`), то же без файла для правила вызова (`base_routes`), суммы по всем маршрутам (`all`) и по изменённым (`group`) с прогнозом без файла (`b50`, `b_s13`, …). Ошибки в файле — 422 с понятной причиной, прочие сбои — 500 с общей фразой. Модель загружается в фоне при старте (≈5 с). Расчёт от момента пульта ≈1 с; от другого момента до ≈15 с, потому что прогноз без файла и состояние ворот для него считаются заново. Один расчёт занимает до ≈900 МБ памяти сверх ≈1,5 ГБ движка, поэтому одновременно идёт один (`UPLOAD_CONCURRENCY`); 20 расчётов за 10 минут с одного IP (`UPLOADS_PER_10MIN`), отказ «сервер занят» в лимит не входит. Запрос без `Content-Length` получает 411.

Демо-файлы — `python scripts/demo_upload.py` → `frontend/public/demo/`, последние 2 часа истории (01.11, 09:00–10:30):

- `zator_0900-1030.csv` — с 09:30 на 200 маршрутах статусы 1–3 (обработка на нашем складе) падают до 5 %, отгрузки не тронуты. Модель ждёт на этих маршрутах −45 % отгрузок за 2 часа (до −59 % к 11:30), срочных вызовов по сети 274 → 236, у 191 маршрута вызов позже.
- `vsplesk_0900-1030.csv` — с 09:30 на других 200 маршрутах статусы 1–3 вдвое выше, отгрузки не тронуты. Модель ждёт на этих маршрутах +32 % отгрузок за 2 часа.

- `obrazec.csv` — образец формата: те же колонки, 3 маршрута по 4 получаса как в истории; ссылка «Скачать образец» стоит под полосой загрузки.

Файл, который повторяет историю, даёт тот же прогноз, что на вкладке «Прогноз» (модель одна и та же, данные те же); экран тогда пишет «В файле те же данные, что в истории, поэтому прогноз не изменился». Как пример он не предлагается: выглядит как копия главного экрана.

Почему затор на сортировке, а не на предыдущем складе: на статусы 4–6 модель почти не реагирует (их обнуление меняет прогноз на 1–3 %), а на статусы 1–3 реагирует сильно. Это стоит говорить на защите: модель смотрит на то, что уже прошло обработку, и видит провал отгрузок за час до того, как он случится.

## Ассистент

### Контракт

```
POST /api/agent
{
  "messages": [{"role": "user" | "assistant", "content": "..."}],
  "view": {"tab": "shift", "route": 471 | null}
}
->
{
  "reply": "1–3 предложения с числами только из функций",
  "actions": [{"type": "open_route", "id": 471}],
  "tools": [{"name": "route_forecast", "args": {"route_id": 471}}]
}
```

Единственное действие — открыть маршрут на экране (`open_route`). Про машины ассистент не считает: их в данных нет, и на такой вопрос он так и отвечает.

### Функции (инструменты модели)

Работают поверх `board.json`; модель данных напрямую не видит.

| Функция | Аргументы | Возвращает |
|---|---|---|
| `route_forecast` | `route_id` | объём на 4 ч, пик, коридор 80 %, история за 8 ч, прогноз по получасам (p10, p50, p90), ошибка и сдвиг на проверке |
| `find_routes` | `order`: `largest`, `least_accurate`, `most_accurate`, `widest_band`; `limit` | маршруты с объёмом на 4 ч, ошибкой на проверке и коридором |
| `network_forecast` | — | товаров за 4 ч по всем маршрутам, пик, коридор 80 %, прогноз по получасам |
| `model_quality` | — | метрика кейса (из 10:30 и по всем моментам), попадание в коридор 80 %, ошибка и сдвиг по дням |

Функции есть в двух копиях с одинаковыми числами: `backend/tools.py` — для модели, `frontend/src/tools.ts` — для сводки в панели и ответов без модели (`frontend/src/brief.ts`: маршрут по номеру, общий прогноз, точность, крупные, точные и неточные маршруты). `route_forecast` открывает маршрут, `find_routes` — первый маршрут списка. Сводка в панели: товаров до конца прогноза, пик, ошибка на проверке, попадание в коридор и три крупнейших маршрута.

### Требования к бэкенду

- Модель — Claude (`claude-sonnet-5-5`, усилие `low`, переменная `MODEL`), официальный SDK `anthropic`. Включены серверные fallbacks (`fallbacks: "default"`): если модель откажется отвечать, запрос сам уйдёт на запасную модель.
- Ключ только в окружении сервера (`ANTHROPIC_API_KEY` или `backend/.env`), в браузер не попадает. Адрес API зашит (`https://api.anthropic.com`), поэтому `ANTHROPIC_BASE_URL` из окружения ключ не получит. Без ключа `/api/agent` отвечает 503.
- Ссылка публичная, поэтому у каждого вопроса есть потолок стоимости: модель видит последние 8 сообщений (не больше 6000 знаков), отвечает не длиннее 1024 токенов, делает до 4 обращений (на последнем функции запрещены) и до 4 функций за раз, на вопрос не больше 45 секунд; повторов при ошибке API нет, перегрузка сразу даёт 503. Длинные прошлые ответы обрезаются до 1000 знаков, а не отклоняются.
- Лимиты: 30 вопросов за 10 минут с одного IP (`RATE_PER_10MIN`), 300 вопросов в час на всех (`RATE_PER_HOUR`), одновременно не больше 4 вопросов (`AGENT_CONCURRENCY`), остальные сразу получают 503 и не занимают сервер. Запрос к `/api/` не больше 64 КБ. На хостинге за прокси нужно задать `FORWARDED_ALLOW_IPS` (адрес прокси), иначе все посетители выглядят как один IP. Для ключа в Console Anthropic стоит поставить лимит расходов: он держит траты при любой ошибке в коде.
- Отказ бэкенда пульт показывает причиной под ответом без модели («Ответ без языковой модели. Слишком много вопросов…»).
- Системный промпт: по-русски, 1–3 предложения, числа только из результатов функций; решение о вызове принимает правило, ассистент его объясняет; на посторонние вопросы отвечает одной фразой.
- Данные пульта уходят в API Anthropic. В плане защиты ассистент на открытой модели внутри компании; для демо выбран Claude.

## План реализации

Каждый шаг — отдельный проверяемый кусок: после него пульт открывается и показывает что-то новое.

### Структура

```
frontend/
  public/board.json          данные, пишет pipeline.py export
  src/
    main.tsx, App.tsx        загрузка board.json, тема, панель ассистента
    data.ts                  типы board.json и загрузка
    format.ts                объёмы (тыс., млн), время, склонения
    plan.ts                  время шага и ширина коридора
    upload.ts                ответ /api/forecast, доска и наложение «исходный прогноз» для Forecast
    tools.ts                 функции ассистента (копия backend/tools.py)
    brief.ts                 ответы ассистента без модели
    motion.ts                параметры анимаций (длительности, пружины)
    components/
      Forecast.tsx           главный экран: объём на 4 часа, проверка, график, маршруты, дни проверки
      AgentPanel.tsx         ассистент: сводка смены плитками и чат
      FileForecast.tsx       вкладка «Свой файл» до результата: примеры и загрузка (результат рисует Forecast)
      Header, Segmented, charts

  app.py                     /api/agent и раздача frontend/dist
  tools.py                   функции ассистента
  forecast.py                сервисная модель для /api/forecast
  requirements.txt, .env.example
Dockerfile
```

### Шаги

Шаги 1–9 сделаны (08.11). 09.11 экран «Почему верить» убран из пульта — его цифры ассистент по-прежнему отдаёт функцией `evidence`. 10.11 образ Docker собран (1,1 ГБ) и проверен: главный экран, загрузка файла и ассистент с ключом Claude работают в контейнере.

| # | Что | Готово, когда |
|---|---|---|
| 1 | Каркас Vite + React + TS + Tailwind, загрузка `board.json`, шапка (момент прогноза, модель, подача) и четыре KPI | KPI совпадают со старой доской: вызвать сейчас, новых машин до 14:30, объём за 4 ч, груз без машины |
| 2 | Пульс склада: история сети 8 ч и прогноз 4 ч с диапазоном, отмечены «сейчас» и пик | график совпадает с блоком сети старой доски |
| 3 | Очередь вызовов: сортировка по времени вызова, фильтры «сейчас / в течение часа / груз без машины / все», поиск по номеру | число строк под каждым фильтром совпадает со старой доской |
| 4 | Карточка маршрута: совет («вызвать сейчас / в 12:00 / не нужно»), график отгрузок с коридором 10–90 %, график груза у ворот в кузовах с моментами вызова и прибытия | для 5–10 маршрутов текст и графики совпадают со старой доской |
| 5 | `plan.ts` и «что если»: подача 30 мин / 1 ч / 2 ч, осторожный сценарий (`c90`); очередь пересортировывается с анимацией | при подаче 1 ч и `c50` пересчитанный `call` совпадает с полем `call` у всех 1000 маршрутов |
| 6 | Экран «Проверка на истории»: потери на машину по пяти правилам с переключателями подачи и кузова, машины и недогруз в день, попадание диапазонов, журнал качества по дням | числа совпадают с `reports/service/lean.json` |
| 7 | `tools.ts`, брифинг и панель ассистента: брифинг при открытии, кликабельные числа, подсказки вопросов; без бэкенда отвечает на типовые вопросы локально | брифинг и ответы содержат только числа из функций |
| 8 | Бэкенд `/api/agent`: FastAPI, функции на Python поверх `board.json`, Claude с функциями, лимит запросов; Dockerfile, который собирает `frontend/dist` и отдаёт его вместе с API | контейнер запускается одной командой, ответы бэкенда и `tools.ts` совпадают на 20–30 вопросах |
| 9 | Полировка: переходы между экранами, выезд панели, счётчики KPI, состояние загрузки и ошибки, светлая и тёмная тема | показ по сценарию защиты проходит без заминок |

Шаги 1–7 не зависят от бэкенда и дают полный показ офлайн. Шаг 8 можно делать параллельно с 6–7: контракт и эталонные числа уже зафиксированы выше.

### Как выглядит и путь показа

Анимации объясняют изменения и отключаются при `prefers-reduced-motion`; параметры — в `frontend/src/motion.ts`.

### Зависимости

React 18, TypeScript 5, Vite, Tailwind 4 (`@tailwindcss/vite`), `motion`, `recharts`, `lucide-react`. Версии Vite и `@vitejs/plugin-react` подобрать совместимые: первая установка `vite@6` с последним `@vitejs/plugin-react` упала на конфликте зависимостей.
